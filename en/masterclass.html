Create HYPERREALISTIC Consistent AI Characters

ComfyUI Mickmumpitz LoRA AI Toolkit

This page breaks down Mickmumpitz's masterclass Create HYPERREALISTIC Consistent AI Characters (761,885 views as of 11/14/2026, published October 7, 2025), referenced in this site's sitography.
The video's stack is open source and local. Let's walk through the key points for building the full ComfyUI pipeline that generates the video.

  • Starting point — a single image. From a single input image (any style), the "Consistent Character Creator" (CCC) workflow — essentially a subgraph of the main pipeline, built on top of Qwen Image Edit's nodes — generates character variations: different poses, expressions, outfit changes (virtual try-on), new scenes and settings.
  • Qwen Image Edit1 — the engine behind the CCC. It's an instruction-based image editing model: from a reference character → it varies pose/outfit/scene through instruction-driven editing — that is, it doesn't generate from scratch, it modifies an existing image following text instructions.
  • Building the dataset. This second part is the dataset creation group, and it “will create the captions and the upscaled images of your character” — the video's own words (minute 5:13). Every image produced lands in the folder named after the character, along with its caption file. The final dataset is a list of image+text pairs, the standard format any LoRA trainer accepts. There's also an upscaling module: Qwen Image Edit generates at a limited native resolution (up to 1024×1024). For a dataset meant to train a “hyperrealistic” LoRA — where fine detail matters (skin, texture, fabric) — generating small and upscaling before saving is the practice recommended by ComfyUI itself: this way the LoRA trains on sharper, more detailed images.
  • AI Toolkit (Ostris) — the engine that runs the LoRA fine-tuning. The dataset is passed to AI Toolkit to train the character's LoRA, fed with the images assembled above. The Qwen → Wan handoff: it's compatible because AI Toolkit trains the LoRA directly targeting Wan 2.2 as the destination model (compatibility here is anything but a given: the LoRA's output format has to match the input the next pipeline step expects — in this case, the Wan video generator).
  • Wan 2.2 — final generation, images and video. The trained LoRA is used with Wan 2.2 to generate the final images and, with a dedicated workflow, the videos2.
  • Runpod — used in two stages: a) for LoRA training, and b) to run the entire ComfyUI pipeline, whose last step is video generation. Runpod is a family of rentable GPU/CPU instances billed by time (dozens of virtual machines, at different power levels and prices). For case b), running ComfyUI itself, RunPod has official templates built specifically for this, pre-installed with ComfyUI and the ComfyUI Manager plugin, in several variants per GPU type. There's even a dedicated "WAN 2.2 Text to Video" template built for ComfyUI with Wan 2.2. Once the pod is deployed, you reach the ComfyUI interface through the browser and run the whole graph there — CCC, dataset creation, final generation with Wan 2.2 — exactly as you would locally, just on rented hardware.

    A cost estimate, calculated from current RunPod prices cross-checked against public benchmarks:

    • LoRA training (a static character with 28 variants, as in the video): $1.50–17, calculated from official RunPod prices × 2-4 GPU hours extrapolated from a documented real-world case (28 images, 2,500 steps, ~2.2h on an RTX 5090).
    • CCC + Dataset Creation pipeline, 3-4 runs: $2–12. The L40 (48 GB, $0.82/h) is the smarter pick — it costs less than the RTX 4090 and has more VRAM, since a real-world test shows Qwen Image Edit can fail to fit in the 4090's 24 GB.
    • Video generation (5-second clips, 3-4 runs): under $0.10 with a 4-step accelerator on a 24 GB GPU (the model takes 71 seconds to produce a clip); about $0.40–0.50 without an accelerator, still on 24 GB (20 steps, the model takes 8.5 minutes/clip). The real cost jump happens when VRAM isn't enough and the system has to offload and reload data mid-run: in those cases even budget GPUs can take over an hour for a single clip, pushing the total cost to $3–4 for a batch of 3-4 clips — not because of the GPU's price, but because of the time lost. A pricier GPU with enough VRAM (e.g. 80 GB) avoids this slowdown and, despite the higher hourly cost, can still end up cheaper overall.

    A total cost estimate is hard to pin down, because each phase is independent, and taking either the minimum or the maximum cost for every phase wouldn't give a realistic min/max for the total. An average might land around $10 for 3 clips of 5 seconds each. That's the cost of building and running a custom pipeline — a character's LoRA in a non-static setting — not directly comparable to the per-video price of an API service like Nano Banana or Seedream, which isn't personalized on any trained set of generated images.

    Automatic correction. The pipeline described in the video has no automated output-evaluation step: every generation has to be checked by eye. A generate→evaluate→correct loop would likely matter more here than in pipelines that only generate static images: video generation is more exposed to defects (the same identity drift described in note 2), and an error caught only at the end of a generation costs far more, in both time and GPU, than one caught on a static image.

  2. 02

    The reference models, a year on

    Every model named in the masterclass has since been superseded. The picture as of November 14, 2026, sourced where possible:

    • Editing, local: Qwen-Image-Edit-2511 — free, Apache-2.0, improved character identity over the version shown in the video.
    • FLUX.2 klein 4B — free, Apache-2.0, about 13 GB of VRAM — this is a feature of the FLUX.2 klein model itself: a single checkpoint handles both text-to-image and editing (instead of two separate models, as with other generation/editing pairs). In the pipeline, that makes it an alternative to Qwen-Image-Edit for the step that builds the character's image dataset. FLUX.2 is only used to produce the dataset images, and the LoRA is still trained targeting Wan 2.2 as before. FLUX.2 doesn't need to "be compatible" with Wan — it only needs to produce good images for the training that follows.
    • Editing, cloud, paid: Nano Banana 2.1 and Seedream 5.5 — the best-quality commercial options, both API-only.
    • Video, local: LTX-2.5 — open weights, free under $10M in annual revenue, 16 GB VRAM minimum. Wan 2.2 remains the last Wan release with open weights; later versions (2.5, 2.6, 3.0) are API-only.
    • Video, cloud, paid: Seedance 2.0, Kling 3.0, Veo 3.1 — among the most-cited commercial options for quality.

    The masterclass's basic architecture still holds up: ComfyUI, the CCC workflow, one LoRA for the lead character. It's worth swapping in Qwen Image Edit 2511 and weighing LTX-2.5 alongside Wan 2.2 for the video stage, keeping in mind that models released only weeks ago have no independent verification yet.

  1. Qwen-Image-Edit is an image-editing model from Alibaba's Qwen team, released August 19, 2025, built on top of the 20-billion-parameter Qwen-Image backbone, under an Apache 2.0 license (open, commercial use included) ( Product Hunt). According to the technical documentation, Qwen-Image uses a three-module architecture (NVIDIA):
    • Qwen2.5-VL — a “frozen” (not retrained) multimodal language model, used to extract text/image features and for semantic alignment, 7 billion parameters — the same family of language models already known as “Qwen,” in its vision-language variant (it reads images and text together);
    • a VAE (encoder/decoder, very small — 54M/73M parameters), responsible for preserving visual/pixel detail;
    • an MMDiT (Multimodal Diffusion Transformer, 20 billion parameters) — the actual generative engine, the diffusion transformer that produces the final image.
    How the three components work together: Qwen-Image-Edit feeds the input image simultaneously to Qwen2.5-VL (for visual-semantic control) and to the VAE's encoder (for visual-appearance control), giving it both text-semantic editing ability and visual-appearance editing ability. In practice: Qwen2.5-VL “reads” the image and the text instruction and decides what to change conceptually (e.g. “put a hat on the cat”); the VAE preserves the visual detail of everything else, so the image doesn't change where it wasn't asked to; the MMDiT generates the final result balancing the two signals.     ↩
  2. Wan 2.2 14B isn't a single-pass model like Qwen Image Edit or Flux: it's a Mixture-of-Experts with a “high-noise” expert (structure/motion) and a “low-noise” expert (detail); AI Toolkit trains both through its “Multi-stage” mode. That means a single training run has to produce and manage two sets of weights, not one — the training pipeline is already more complex than a single image model's.
    That constraint carries over to inference too: Wan 2.2's MoE architecture requires adjusting the weights in BOTH expert networks to get consistent results. On the community side, WAN 2.1 LoRA compatibility generally holds up well, as does WAN 2.2 “low noise” LoRA compatibility (don't use “high noise” LoRAs there), and LoRA strength may still need adjusting — meaning even within the same Wan ecosystem, LoRAs aren't automatically interchangeable without tuning.
    And for video specifically, character consistency in WAN 2.2 I2V warps during motion — an “identity drift” and face-deformation problem that's documented and addressed with dedicated guides, not a minor detail.     ↩
